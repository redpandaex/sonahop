# SonaHop 第一阶段设计

## 目标与已确认范围
最终首版为 Windows 11 与 Android 16 的双向音频：两台 Android 可同时收听；麦克风模式只选一台发送，所有收听暂停。两种模式互斥。先兼容已有虚拟音频设备，独立 Rust 核心未来接入 Tauri 与更多平台。

本阶段交付 Windows 系统播放声音采集 CLI。它是发送端的基础验证工具，不采集 Windows 麦克风，也不新增面向用户的录音产品功能。网络、Tauri 与 Android 在后续阶段接入。

## 当前阶段的结构
- `sonahop-core`：音频格式、平台采集接口、f32 数据校验和用于调试的 WAV 写入。
- `sonahop-platform-windows`：枚举 Windows 播放设备，选择 Render 端点并以 WASAPI loopback 采集。
- `sonahop` CLI：设备列表、选择音源、限定时长采集、取消和结果摘要。
- 依赖方向：Windows 后端依赖 core；CLI 依赖两者；core 不依赖 OS 或 Tauri。

第一阶段将公共接口放在 core 中。待有第二个真实平台实现后，再决定是否拆分独立 api crate，避免为尚未实现的后端创建空模块。

## 行为
- `devices` 显示播放设备及默认设备，支持 JSON；枚举不会开始录音。
- `capture --output <path> --seconds <1..60> [--device <id>]` 明确启动系统播放声音采集，输出 float32 WAV，保留所选设备的采样率、声道与已知扬声器布局；未知布局不推断位置。
- 必须显式提供文件路径，已有文件不覆盖；无设备、无音频数据、等待超时或格式错误返回明确失败。
- 静音标记按帧数写零；不连续数据记录计数。停止、错误和 Ctrl+C 都释放设备，WAV 正确收尾。
- 限定采集窗口和最大帧数，不允许一次设备读取消耗无界内存或无限等待。
- 本地 WAV 仅用于诊断，不进入 Git。实际系统声音采集验证需用户单独确认；此前只执行合成数据测试及设备枚举。

## 验收
- CLI 初始化和依赖添加通过 `cargo new/add` 完成，workspace 配置只做 CLI 不覆盖的必要编辑。
- 核心测试检查手工给定 f32 数据、静音、帧对齐、异常数据、WAV 头和最大帧数。
- CLI 测试检查非法时长、缺少输出参数和已有文件保护，且不触碰真实音源。
- `cargo test --workspace`、格式检查、Clippy 和 release 构建通过。
- Windows 真机设备枚举通过；播放测试音并采集的结果单独记录，未经授权或未测试不宣称已通过。

## 后续阶段
1. Tauri 外壳、Android 原生服务及最小原生构建。
2. 固定参数 Opus/QUIC 链路，单接收端再扩展双接收端。
3. 手机麦克风到已有 Windows 虚拟输入，互斥切换、后台和双机验收。

已确认的设备为当前 Windows 11、小米 17 Pro Max 与联想 Y700 四代（Android 16）。旧 OpenSpec 文档保留为需求参考，后续主要按此设计与阶段计划推进。
