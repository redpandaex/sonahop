# Windows 虚拟音频设备 — 后续方案

状态：架构记录，尚未实现驱动，也不改变当前 Windows 音频设置。

用户提出将连接的 Android 播放器作为 Windows 音频设备，默认关闭，仅在支持时允许开启。本轮用户同时确认：手机麦克风与电脑系统声音保持独立，不增加麦克风监听或混音。

## 设备与路径

- SonaHop Speakers（播放设备）：Windows 应用 → Windows 虚拟播放端点 → Rust 音频发送 → 用户选定的 Android 播放器。
- SonaHop Microphone（录音设备）：用户启动并获得电脑批准的 Android 麦克风 → Rust 音频接收 → Windows 虚拟录音端点 → Windows 应用。
- 这两个端点独立；录音设备有声音，不表示 Windows 会把它播放出来。麦克风监听/混音需要另一个显式功能，默认关闭，当前不实现。

## 接入顺序

1. 先兼容用户已经安装的虚拟音频线。对麦克风，把接收到的声音写入其播放端，Windows 应用选择成对录音端。虚拟扬声器路径则需要增加该虚拟线成对录音端的捕获后端，不能直接沿用当前排除 SonaHop 的全系统进程捕获。
2. 后续提供专门的 Windows 驱动及安装包，暴露以上播放/录音端点。驱动只负责 Windows 音频端点、PCM 缓冲及用户态交接；编解码、传输、会话和权限状态继续由 Rust 内核负责。
3. 先用单一 SonaHop 播放设备，在应用中选择 Android 接收者；不在每次手机连接时重新安装驱动。每台远端单独对应 Windows 音频端点是后续扩展。

## 开关与能力判断

- 开关默认关闭；安装了兼容的虚拟设备后端、Windows 版本受支持并且端点可用时才允许开启。
- Android 端验证已有播放能力、协议能力与连接状态。支持条件主要取决于 Windows 后端，而非某个手机品牌。
- 不自动安装驱动、修改系统默认播放/录音设备、开启麦克风、启用监听或改变本地音量。
- 断线时结束当前音频会话并显示原因；麦克风重新连接后仍遵循用户启动和电脑批准流程。

## 仍需解决

驱动签名与安装/卸载、设备生命周期、驱动时钟与网络时钟偏差、PCM 有界缓冲、格式转换，以及应用退出后的端点状态。Rust/Tauri 应用自身不能仅通过注册一个设备名称替代这些工作。

参考：[Microsoft SysVAD 驱动示例](https://github.com/microsoft/Windows-driver-samples/tree/main/audio/sysvad)。SysVAD 是驱动开发起点，仍需实现 SonaHop 的 PCM 交接和安装分发。
