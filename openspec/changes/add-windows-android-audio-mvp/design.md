# Design

## Context

需求动机与范围见 [proposal.md](proposal.md)，行为合同见本变更的六份 `specs/*/spec.md`。代码仓库当前只有 OpenSpec 和项目约定，没有 Rust 或 Tauri 应用。

已在当前 Windows 主机验证：Windows 11 专业版，Rust 1.98.1 / MSVC 工具链，Node 24.21.0，pnpm 11.25.0，JDK 21，Visual Studio C++ 工具可用。Android SDK 位于 `D:\Android\Sdk`，存在 API 36、37.0 平台、NDK 30.0.16248370 和 ADB。这些证明开发工具存在，尚未证明 Android 原生依赖能成功编译。

机型、系统与 USB 可用性来自用户；两台 Android 尚未连接检查。实施目标以 Windows 11 和这两台 Android 16 为准，较旧版本和其他平台不作验证声明。

## Goals / Non-Goals

**Goals:**
- 共享引擎能够通过 CLI、Tauri 和 Android 服务入口复用，平台后端不改变会话与协议语义。
- 同一个电脑音源可以编码一次，并向两个独立接收端发送；慢接收端不阻塞另一个。
- 麦克风所有权、模式互斥和旧流拒绝可以通过无硬件的测试验证。
- 音频流的运行寿命由原生引擎及服务持有，界面只能发命令和读状态。
- 每个可见能力都具备诊断信息和对应验收记录。

**Non-Goals:**
- 暂不设计动态库插件 ABI；按编译目标装配平台后端。
- 本变更采用固定编码参数和缓冲设置；不实现复杂质量自适应。
- 多接收端独立播放，不设跨设备采样级同步目标。
- 其余产品范围见 proposal，避免在此重复。

## Decisions

### 1. Cargo workspace 与明确的依赖方向

通过 `cargo new` 创建库和调试 CLI，通过 `pnpm create tauri-app` 创建 Tauri 入口，通过 `cargo add` / `pnpm add` 管理依赖。优先读取对应 CLI 的当前帮助；只对 CLI 未覆盖的 workspace 连接和项目配置进行小范围编辑。

计划结构：

```text
crates/
  sonahop-api/                 平台接口、音频格式、错误和能力描述
  sonahop-core/                会话、协议、编解码、缓冲和连接
  sonahop-platform-windows/    WASAPI 采集、播放及设备事件
  sonahop-platform-android/    原生音频后端
apps/
  sonahop-cli/                 枚举设备、采集验证与调试入口
  sonahop-ui/                  Tauri + React/TypeScript
    src-tauri/                装配和命令桥接
    src-tauri/gen/android/    Kotlin 权限与前台服务桥接
```

依赖为：core → api；各平台后端 → api；应用入口 → core + 当前平台后端。共享核心不导入 Tauri、Windows 或 Android 类型。通过窄接口描述采集、播放、能力、设备变化和生命周期。

考虑过把平台分支直接放进 Tauri 命令中，或从一开始创建运行时插件系统。前者难以无界面测试，后者需要额外 ABI、版本和加载管理；首版采用编译时后端注入。Linux/macOS 将来按同一接口加入，不先创建声称已经可用的空后端。

### 2. 单一会话所有者与两阶段模式切换

电脑端控制器拥有全局状态：Stopped、Listening、Microphone(selected_peer)、Transitioning。连接状态按设备单独记录，不与全局音频模式混为一项。

命令经有界控制通道串行处理；每台设备的连接、流编号和共享意图由该控制器管理。UI 重开只读取快照，不构造第二个引擎。

切换流程：
1. 检查虚拟设备、手机权限和原生服务启动条件，要求手机在可见界面确认录音。
2. 停止旧流并清空旧接收缓冲；未能及时确认停止的设备退出本次共享。
3. 为新模式分配新流编号，提交所有权，再启动新音频方向。
4. 启动失败则回到 Stopped 并报告错误；前置条件失败则保持原模式。

电脑的 Stop 停止所有共享；Android 的 Stop 结束本设备参与的流。当前麦克风设备停止时全局麦克风模式结束。另一个已连接设备不自动取得录音权。

相比多个入口直接调用 start/stop，此方案将重复请求、模式竞争和停止后重新连接统一处理。停止操作需取消工作线程、释放设备和阻止旧编号音频进入下一次会话。

### 3. 原生音频与后台生命周期

Windows 后端首选 WASAPI shared-mode loopback，使用用户选定输出设备及实际混音格式；设备枚举、默认变化和移除通过平台事件回报。虚拟麦克风通过向已有虚拟通路的播放入口写入，再由外部软件读取其录音出口实现。

首版不自动安装驱动，也不自动更改电脑的默认音频设备、音量或防火墙。虚拟通路的端点配对需要用户配置并通过实际录音软件验证，设备名称匹配只作辅助提示。

Android 首选 Rust 调用 AAudio 的输入和输出后端，Kotlin 管理录音权限、音频焦点、设备事件、通知和前台服务。先用最小编译与真机音频探针验证 AAudio 绑定和 native 依赖；若原生封装需要调整，更新设计中的实现记录，保持需求合同不变。

播放服务声明对应播放类型；录音服务声明对应麦克风类型，并在可见界面授予 RECORD_AUDIO 后启动。Kotlin 服务通过 JNI 持有同一 Rust 会话实例，Tauri WebView 暂停不改变会话所有权。调用停止/关闭设备的操作不得在音频回调内部执行。

本次不需要 Android 应用声音采集，因此不引入 MediaProjection。相比让 Web Audio 或界面事件持续推动播放，原生服务与音频后端能独立处理锁屏和界面重建。

### 4. 固定参数音频流水线与独立接收端

内部使用明确采样率、声道和布局的 f32 PCM；编码前转换为 48 kHz。初始设置为 Opus 10 ms 帧，电脑音源双声道 128 kbps，手机麦克风单声道 32 kbps。它们是待调试的工程参数，不是音质或延迟保证。

```text
采集回调 → 有界 PCM 缓冲 → 重采样/分帧/编码 → 发送工作线程
接收工作线程 → 有界抖动缓冲 → 解码/时钟补偿 → 有界 PCM 缓冲 → 播放回调
```

音频回调仅移动预分配数据并更新轻量计数；网络、日志、分配和编码由工作线程完成。采用独立所有者及 SPSC 缓冲；两个接收端共享已编码内容，各自使用有界发送队列和接收缓冲，不能用两个消费者读取同一个单消费者 PCM 队列。

首版抖动缓冲目标先设 50 ms，上限先设 100 ms；其他队列也设固定帧数和时间上限，在诊断中分别显示。迟到数据丢弃并记录；缺帧使用解码器的基本丢包隐藏。静音期间维护音频时间线或明确重置流，不能在声音恢复后重播积压。

输出设备时钟与输入时钟不一致，通过重采样及缓冲占用的慢速反馈做基础漂移补偿。此补偿保持编码参数固定，不等于本次承诺自适应码率。考虑过直接原始 PCM 传输；Opus 能减少首版双接收端的载荷，代价是 native codec 构建，需要先验证目标平台。

### 5. QUIC 连接、音频协议与配对

每台 Android 建立独立 QUIC 连接；可靠流发送有长度边界的控制消息，Datagram 承载音频。音频包包含协议版本、流编号、序号、48 kHz 采样时间戳和编码载荷。开始消息确定方向、编码和声道；接收端校验长度、身份、流编号、格式与当前模式。

帧必须符合连接的最大 Datagram 大小；用编码器目标码率和帧长度控制载荷，不依赖 IP 分片。全局模式变化、重连或设备替换分配新流编号，迟到和重复包不会重新进入播放。

首版使用手工地址接入。电脑显示可复制的连接信息和证书指纹；手机绑定预期电脑身份，双方在开放配对期间明确确认设备。保存已配对公钥/证书身份，后续重新连接验证记录；配对未完成的连接仅能执行配对操作，无法访问音频。使用现有 TLS 实现，不自行设计加密算法，私钥存放于平台应用私有数据位置。

连接恢复按设备单独退避，用户 Stop 清除共享意图。心跳丢失后先标断线并清理过期媒体，控制连接恢复不自动绕过 Android 录音启动条件。

相比可靠流持续传音频，Datagram 不等待过期媒体重传，但需要应用处理乱序、丢失和排队。QUIC 拥塞控制不能代替接收端播放反馈。首版不引入 mDNS、互联网中继或专门 USB 网络隧道。

### 6. UI、诊断和发布入口

React/TypeScript 是初始 UI 技术选择，Tauri 提供桌面与 Android 外壳；共享逻辑留在 Rust，界面只调用设备枚举、配对、模式切换、停止、状态和诊断接口。以设备列表、两个互斥模式、输入输出选择和停止入口为最小界面。

按 peer/stream 输出网络 RTT、序号缺口、迟到/丢弃、队列毫秒数、处理耗时和播放 underrun。缺口待乱序窗口关闭后再计入，不能看到跳号就断言永久网络丢包。诊断默认不包含原始音频。

开发与构建命令记录在 README；Cargo.lock 和 pnpm 锁文件由 CLI 生成并提交。交付包含 Windows 安装包和可部署 APK，但构建成功与真机通过分别记录。APK 只用调试签名开始物理测试，正式分发签名和许可证决定在发布准备时处理。

## Risks / Trade-offs

- [Android 厂商后台策略导致锁屏中断] → 两台机型分别验收前台服务、权限与锁屏；需要用户调整后台设置时记录具体原因和步骤。
- [Opus/AAudio 与 NDK 的构建组合尚未验证] → 首个实施阶段先编译两平台最小原生入口；使用生成的构建配置和 sdkmanager CLI 准备匹配版本，避免先写完整 UI 再发现无法构建。
- [虚拟音频设备存在播放入口/录音出口混淆] → 分别标注两端并用实际外部软件验证；不自动安装或替换用户设备。
- [固定码率遇到差网络仍会丢音] → 有界队列、基本丢包隐藏和明确诊断；不承诺任意网络零卡顿。
- [采样格式、静音与时钟差异造成杂音或积压] → 对格式、时间线和缓冲边界建立测试，真机记录实际设备格式与运行计数。
- [两台接收端有播放时间差] → 本次保证各自工作及独立恢复，不设多房间精确同步标准。
- [会话竞争或重连导致错误音源恢复] → 串行控制、明确共享意图、单麦克风所有权及新流编号；旧流与未选中发送者测试必须通过。

## Migration Plan

这是空仓库的首个应用变更，没有旧用户数据迁移。按工程/原生构建、Windows 采集、协议与本地模拟、Android 单接收端、双接收端、麦克风及虚拟通路、模式与恢复、安装包和验收的顺序交付。

先保留各阶段可独立运行的调试入口。失败时停止服务并释放设备，回退到已验证的构建；应用不会为本次自动安装驱动或修改默认音频设备。调试录音仅在用户明确操作下写入忽略的测试输出目录。

## Verification Matrix

| 验证项 | Windows 11 | 小米 17 Pro Max / Android 16 | 联想 Y700 四代 / Android 16 |
| --- | --- | --- | --- |
| 构建与部署 | 安装包、CLI、设备枚举 | APK 与 native 库装载 | APK 与 native 库装载 |
| 单端收听 | 系统音源可采集 | 播放与正常输出切换 | 播放与正常输出切换 |
| 双端收听 | 独立队列与状态 | 与 Y700 同时播放 | 与小米同时播放 |
| 麦克风 | 虚拟通路与外部软件输入 | 作为唯一发送端 | 作为唯一发送端 |
| 后台 | UI 与引擎状态一致 | 锁屏、切后台、界面重开 | 锁屏、切后台、界面重开 |
| 故障与切换 | 模式互斥、所有权和恢复 | 断线/撤权/停止 | 断线/撤权/停止 |

自动化验证覆盖：格式与数据边界、序号/旧流、互斥模式、重复停止、授权失败、模拟慢接收端及有界内存、编解码和采样转换。采用虚拟音源/时钟测试时序，避免依赖测试主机的麦克风。

真机基准：同一正常局域网、可采集测试音源、先用扬声器或有线输出；两台同时收听连续 10 分钟，其中后 5 分钟锁屏。随后每台作为麦克风单独验证 5 分钟，再执行模式切换、停止重启、单端断线恢复和权限撤销。

基准期应没有非预期的持续停播、明显回环、错误设备输入或队列持续增长。所有诊断计数与实际异常均记录；有异常就定位修复或明确标为未通过，不能以编译成功替代验收。记录实际录音软件、虚拟设备端点、构建版本和手机系统版本。真正端到端延迟使用声音/回环测量另行记录，不由 RTT 推算。
